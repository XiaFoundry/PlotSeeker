# PlotSeeker 项目开发总计划

> 项目类型：基于 Bangumi Archive 的多实体 RAG 检索系统
> 开发方式：分阶段实施、每阶段实际验收、以评测结果驱动优化
> 核心目标：根据用户提供的模糊剧情、角色特征、世界观设定或碎片线索，检索并定位最可能对应的作品。

## 一、项目定位与总体目标

### 1.1 要解决的问题

传统的作品搜索主要依赖作品名称、标签等关键词。用户如果只记得某个剧情片段、人物特征或模糊设定，往往很难找到目标作品。

PlotSeeker 希望解决这一问题。

示例：

- “主角好像是一个失去记忆的魔王，故事发生在现代学校。”
- “有一部动画，角色的能力和时间循环有关，但我忘了名字。”
- “记得某一话里妹妹用脚抵住门，不让人进来。”
- “找一部很老的游戏，只记得其中有个会说话的白色生物。”

系统需要综合作品简介、角色信息、章节描述、别名和实体关系，召回可能的作品，并给出能够核查的匹配依据。

以上均为功能示例，不代表当前数据一定包含对应线索。

### 1.2 核心技术目标

本项目的核心不是调用 LLM，也不是搭建复杂 Agent，而是完成一个可验证的 RAG 工程闭环：

1. 将大规模原始 JSONL 数据转化为可查询的结构化知识库。
2. 将作品、角色和章节转换为适合语义检索的文档。
3. 构建持久化向量索引和中文关键词索引。
4. 实现关键词检索、向量检索、结果融合及实体关系扩展。
5. 通过有标准答案的测试集验证检索效果。
6. 提供稳定 API、可复现的评测报告和运行文档。

Agent 作为后续扩展，用于规划补充检索、消歧和追问，而不是项目第一阶段的重点。

### 1.3 项目成功标准

项目最终应当能够证明：

- 数据处理流程可重复运行，且原始数据不会被修改。
- 每条检索结果都能追溯到对应实体及原始来源。
- 混合检索相较于单一检索方案的效果经过实测。
- 向量索引构建过程可恢复，能够应对中断。
- 检索服务可通过 API 调用，错误和资源占用可监控。
- 所有展示在 README 和简历中的数据均有实际测试记录支持。

### 2.1 已知工作区状态

| `character.jsonlines`          | 22.4 万    | 角色信息             |

### 2.2 数据处理原则

- `data/raw/` 为原始数据目录，只读，不覆盖、不删除、不原地清洗。
- `data/processed/` 保存清洗结果、检索文档、临时转换后的数据。
- `storage/` 保存 SQLite 数据库和向量索引等可重建产物。
- 原始字段与业务字段分开管理，任何字段转换都要有明确规则。
- 数据量、空值率、孤儿记录数等结论必须由程序实际计算。
- 不因某个实体暂时没有向量而从结构化数据库中删除它。
- 未验证字段含义前，不要将数字码值自行解释为固定业务含义。

## 三、技术架构

### 3.1 技术栈

| 模块         | 首选方案           | 说明                             |
| ------------ | ------------------ | -------------------------------- |
| 语言         | Python 3.11+       | 数据处理、检索和服务             |
| 结构化数据库 | SQLite             | 实体、关系和来源信息             |
| 关键词检索   | SQLite FTS5        | 名称、别名、标签和关键词         |
| 向量数据库   | Chroma             | 持久化语义向量检索               |
| Embedding    | BGE-M3             | 中文、多语言语义向量             |
| 文本预处理   | jieba、可选 OpenCC | 中文分词及繁简归一实验           |
| API          | FastAPI            | 对外提供检索服务                 |
| 测试         | pytest             | 单元、集成及接口测试             |
| 数据中间格式 | JSONL、Parquet     | 按场景选择，不强制所有数据转格式 |

具体依赖版本在环境初始化阶段确定，并写入锁定文件。不要在没有必要的情况下引入多个重复功能的框架。

### 3.2 架构分层

```
Bangumi Archive JSONL
        |
        v
数据审计与清洗
        |
        +------> 原始数据 / 质量报告
        |
        v
结构化数据导入
        |
        +------> SQLite 实体与关系
        |
        +------> SQLite FTS5 关键词索引
        |
        v
检索文档构建
        |
        v
Embedding 批量编码
        |
        v
Chroma 向量索引
        |
        v
关键词召回 + 向量召回
        |
        v
RRF 融合 + 关系扩展
        |
        v
候选作品 + 可追溯证据
        |
        +------> 评测脚本
        |
        +------> FastAPI
                    |
                    v
               用户查询接口
```

LLM 和 Agent 不属于上述基础检索链路的必要依赖。

## 四、开发阶段与验收标准

所有阶段按顺序推进。Harness 完成当前阶段后，必须实际运行测试、汇报结果，并等待人工确认后再进入下一阶段。

### P0：环境初始化与项目骨架

**目标：建立规范、可复现的开发环境。**

实施任务：

1. 检查现有文件与 `readme.txt`，避免覆盖已有内容。
2. 建立下列目录：

```
PlotSeeker/
├── data/
│   ├── raw/
│   └── processed/
├── storage/
├── scripts/
├── src/
│   ├── ingestion/
│   ├── embeddings/
│   ├── retrieval/
│   ├── evaluation/
│   ├── agent/
│   └── api/
├── tests/
├── benchmarks/
├── docs/
├── scratch/
├── requirements.txt
├── .gitignore
└── README.md
```

1. 配置 Python 环境和依赖版本。
2. 配置 `.gitignore`，默认排除虚拟环境、模型缓存、可重建索引、大型中间数据和临时文件。
3. 将临时实验脚本放入 `scratch/`，正式、可复用的工具放入 `scripts/`。
4. 编写最基本的项目运行说明。

**验收标准：**

- 环境可以根据依赖文件重新安装。
- 项目目录与规划一致。
- 原始 JSONL 文件没有发生变化。
- 临时文件、模型文件和大型数据库不会意外进入 Git 提交。

**停止条件：**环境安装失败或依赖冲突时，先解决环境问题，不进入数据处理阶段。

### P1：全量数据审计

**目标：确认数据质量，为后续 Schema 和索引策略提供依据。**

开发文件：

- `scripts/audit_data.py`
- `docs/data-audit.md`

实施任务：

1. 使用流式读取方式解析 JSONL，不将整个大文件一次性加载到内存。
2. 统计每个文件的实际行数、解析失败数、空行数和文件大小。
3. 对主实体统计 ID 唯一性、缺失字段比例及主要文本长度分布。
4. 统计作品类型、平台、日期、标签等字段的分布。
5. 检查关联表两端的实体是否存在，统计孤儿记录、重复关联和缺失关联。
6. 抽样分析 `infobox` 的实际格式，确认别名、中文名、性别、生日等字段的解析方式。
7. 评估 `episode.description` 的内容质量，识别实际剧情描述与制作人员名单、制作信息等非剧情文本。
8. 统计作品简介、角色简介及其他字段中的中文、日文、繁体中文等文本覆盖情况。
9. 输出建议索引范围及依据，但不在本阶段删除或裁剪原始数据。

**重要规则：**

- 审计报告必须由脚本生成，不能直接将规划中的估算数字写成实测结果。
- 对无法确定含义的字段，只报告分布与样例，不自行猜测。
- 对异常记录应保留样例或可定位的 ID，便于后续排查。

**验收标准：**

- 9 份文件均有完整的读取统计。
- 解析错误可定位，异常记录数量有明确报告。
- 主表与关联表的完整性有量化结果。
- 报告给出首期数据范围的推荐方案及理由。

### P2：SQLite 结构化数据库

**目标：建立完整、可追溯、可重复导入的结构化数据层。**

开发文件：

- `scripts/import_sqlite.py`
- `src/ingestion/`
- `tests/test_import_sqlite.py`

建议建立的主表：

- `subject`
- `character`
- `episode`
- `person`

建议建立的关联表：

- `subject_characters`
- `subject_persons`
- `subject_relations`
- `person_characters`
- `person_relations`

另建立必要的码值说明与来源记录。具体表结构根据原始数据实际字段确定，不得擅自丢弃业务字段。

实施任务：

1. 为实体 ID、作品 ID、角色关联和常用查询条件建立索引。
2. 设计合理的数据类型、主键及必要的唯一约束。
3. 对可验证的关系设置外键，或在导入阶段执行等价的完整性检查。
4. 使用事务和批量插入提高导入效率。
5. 提供 `--limit` 冒烟测试模式，以及可重复执行的完整导入模式。
6. 导入后执行行数对账、主键检查、关系完整性检查和抽样回查。
7. 支持从空数据库重建，避免重复运行造成重复记录。
8. 保留原始实体 ID，使 SQLite 记录可以追溯到原始 JSONL。

**注意事项：**

- 限量导入时，必须同步限制关联表的两端实体，不能把测试模式的孤儿关系误认为全量数据问题。
- SQLite 外键约束需要显式启用并验证。
- 数据库重建应有明确的覆盖保护，避免误删已有产物。

**验收标准：**

- 小规模导入成功，完整导入流程可执行。
- 主键和行数对账通过，所有异常均有报告。
- 可以通过 SQL 从角色查到所属作品，也能从章节查到作品。
- 重复执行不会生成重复数据。

### P3：检索文档构建

**目标：将结构化实体转换为适合语义检索的文本。**

开发文件：

- `scripts/build_documents.py`
- `src/ingestion/document_builder.py`
- `tests/test_document_builder.py`

第一版优先构建三类文档。

**A. 作品文档**

建议包含：

- 中文名称、原始名称及别名
- 作品简介
- 标签
- 类型与平台
- 从 `infobox` 中可靠提取的其他名称信息

**B. 角色文档**

建议包含：

- 角色名称与别名
- 角色简介
- 所属作品名称
- 与作品关联的必要信息

角色文档应能独立检索，即使用户只记得角色特征，也有机会找到目标作品。

**C. 章节文档**

建议包含：

- 所属作品名称
- 章节名称、集数及相关标识
- 经过质量判断的章节描述

章节数据质量参差不齐。制作名单或其他无关描述不能被当作剧情证据。第一版应根据 P1 审计结果制定过滤规则，并保留过滤原因，后续通过评测验证规则是否过严。

**文档元数据至少包含：**

`entity_type`、`entity_id`、`subject_id`、`source`。

其他字段按实际需要增加，例如名称、作品类型、年份和 NSFW 标记。

**实施要求：**

1. 原始 `infobox` 保留在结构化数据库，单独实现可测试的解析器。
2. 解析器应容忍字段缺失、格式异常和不同的别名写法。
3. 文档中保留可用于精确匹配的原始名称和别名。
4. 设置文档长度上限，并记录截断策略。
5. 每个文档必须有稳定 ID，便于重复构建、更新和追踪。
6. 通过抽样检查，防止字段错位、错误关联和无关内容大量进入文档。

**验收标准：**

- 每类文档均有清晰模板。
- 文档生成可重复执行。
- 随机抽取至少 50 条文档，可追溯到对应原始实体。
- 别名和中文名称能够正确进入文档。
- 文档数量与生成日志中的有效、过滤、失败数量一致。

### P4：建立向量索引

**目标：建立持久化的语义检索能力。**

开发文件：

- `scripts/build_index.py`
- `src/embeddings/`
- `tests/test_vector_index.py`

实施任务：

1. 选择并固定 Embedding 模型版本。
2. 先用不超过 1 万条真实文档进行小规模测试。
3. 测量编码速度、峰值内存、索引体积、查询延迟及检索结果质量。
4. 根据实测结果确定批次大小和后续扩容方案。
5. 将向量写入 Chroma 持久化索引。
6. 按作品、角色、章节分 collection，或通过统一 collection 的元数据过滤实现；根据小规模实验决定，不预先过度优化。
7. 提供索引统计、重建、断点恢复和失败记录功能。
8. 保证查询向量与入库向量使用兼容的同一 Embedding 模型及相同的必要预处理规则。

**资源管理要求：**

- 不默认一次性对全部数据编码。
- 批量处理时控制内存和显存占用。
- 遇到中断后可以从已完成的文档继续，不必从头开始。
- 不能只根据最大 ID 判断索引已经完整。
- 对于被删除或修改的文档，应在正式增量机制中处理，避免旧向量长期残留。

**验收标准：**

- 1 万条文档完成编码、写入与查询。
- 索引重新打开后仍能正常检索。
- 文档与索引记录可以核对。
- 断点恢复和重建至少各通过一次实际测试。
- 资源开销被记录，并据此决定下一阶段的索引规模。

**阶段原则：**小规模检索成功之前，不进行百万级全量编码。

### P5：关键词检索与混合召回

**目标：实现真正可用于作品定位的检索链路。**

开发文件：

- `src/retrieval/`
- `tests/test_keyword_retrieval.py`
- `tests/test_hybrid_retrieval.py`

#### 5.1 关键词检索

基于 SQLite FTS5 构建作品、角色和章节关键词索引。

需要重点处理：

- 中文名称与别名
- 日文原名
- 繁简混排
- 用户输入中的标点、空格与无意义词
- 短语和短文本匹配

中文分词方案不能仅凭理论确定。先对 jieba 预分词与字符 bigram 等候选方案做小规模对比，再确定默认方案。

所有入库与查询预处理逻辑必须复用同一模块。

#### 5.2 向量检索

输入用户的自然语言描述，召回语义相近的作品、角色或章节。

向量检索的目标是找出表达不同但含义接近的线索，而不是替代名称和别名的精确匹配。

#### 5.3 融合召回

第一版采用 Reciprocal Rank Fusion（RRF）融合关键词和向量检索结果。

基本计算方式：

[
RRF(d)=\sum_{r}\frac{1}{k+\operatorname{rank}_r(d)}
]

其中 (r) 表示不同的检索结果列表，(k) 使用常见默认值 60 作为初始配置，后续可通过评测调整。

不直接将不同检索系统的原始分数相加，因为它们的分数尺度未必可比。

#### 5.4 关系扩展

当召回结果是角色或章节时，通过结构化关系定位对应作品。

例如：

```
用户描述
   |
   v
命中角色文档
   |
   v
subject_characters
   |
   v
所属作品
   |
   v
合并其他命中证据
   |
   v
候选作品排序
```

同一作品如果被简介、角色、章节等多种线索同时命中，可以获得更强的支持，但不能因为关联数量多就无条件提高排名。

#### 5.5 证据返回

每个候选作品至少提供：

- 作品 ID、名称和类型
- 最终排序分数
- 命中的角色或章节
- 命中来源和可核查的文本片段
- 关键词召回与向量召回的排名
- 关系扩展路径

证据应来自实际数据，不允许 LLM 自行编造剧情来解释检索结果。

**验收标准：**

- 提供命令行检索 Demo。
- 关键词、向量和混合检索均可独立运行。
- 角色与章节命中能够正确映射到作品。
- 同一查询可以重复获得一致的基础结果。
- 不存在的实体不会被静默伪装成有效证据。

### P6：建立评测体系

**目标：量化证明系统是否真的有效。**

开发文件：

- `benchmarks/`
- `src/evaluation/`
- `docs/evaluation.md`

#### 6.1 测试集构建

第一阶段先整理 100 条左右带标准答案的查询，之后逐步扩充。

建议覆盖：

- 作品简介和世界观
- 角色特征
- 章节或名场面
- 作品别名和日文名称
- 碎片化线索
- 简繁混排
- 信息不足、数据缺失或存在歧义的查询

每条记录至少包含查询文本、标准答案 `subject_id`、可接受答案（如有）、线索类型和标注说明。

测试集应尽可能包含真实、独立的模糊描述，不要仅将数据库简介改写成问题，否则会高估检索能力。

#### 6.2 基线对比

至少比较三种方案：

1. 纯关键词检索
2. 纯向量检索
3. 关键词与向量混合检索

后续可增加关联扩展、reranker 等消融实验，确认各个模块是否真正带来收益。

#### 6.3 评测指标

- Recall@5：标准答案是否出现在前 5 个结果中。
- MRR@10：标准答案首次出现的排名质量。
- Top-1 Accuracy：第一名是否为可接受答案。
- P50/P95 延迟：检索速度。
- 索引体积与峰值内存：资源开销。

对于允许多个正确作品的查询，应在测试集里明确可接受答案，并统一计算口径。

#### 6.4 失败案例分析

为未命中的查询记录原因：

- 原始数据缺失
- 文本质量差
- 别名解析失败
- 关键词分词问题
- 向量召回失败
- 关系扩展失败
- 排序不合理
- 问题本身存在歧义

每轮优化必须重新运行相同测试集，并记录修改前后的指标。

**验收标准：**

- 一条命令可以重复运行所有基线评测。
- 结果自动输出到文件。
- 每项指标都能追溯到具体测试样本。
- 报告如实呈现结果，包括没有提升或出现退化的情况。

### P7：资源扩容与检索优化

**目标：在保证质量的前提下扩大覆盖范围。**

只有小规模闭环与评测完成后，才进入此阶段。

实施任务：

1. 根据数据质量和评测结果逐步扩大作品索引。
2. 加入高价值角色和章节文档。
3. 测量每增加一类文档带来的 Recall、MRR、延迟和存储变化。
4. 根据需要增加 reranker，例如 BGE Reranker 系列模型。
5. 评估热门度、年份、作品类型等先验是否能改善排序。
6. 处理文档更新、删除和索引版本管理。
7. 形成可复现的索引构建与发布流程。

**原则：**不追求盲目索引全部数据。只有当新增数据确实改善检索覆盖或质量，且资源开销可接受时，才扩大索引。

### P8：FastAPI 服务与完整文档

**目标：把本地检索能力封装为可运行的服务。**

开发文件：

- `src/api/`
- `tests/test_api.py`
- `docs/architecture.md`
- `README.md`

建议接口：

- `GET /health`：健康检查。
- `GET /search?q=...&top_k=10`：作品检索。

检索响应应包含候选作品、分数和证据，并明确区分原始数据字段与系统生成的排序信息。

实施任务：

1. 对查询参数进行验证。
2. 处理空查询、超长查询和非法参数。
3. 为请求设置合理的超时及异常处理。
4. 避免每个请求重新加载模型或重新打开完整索引。
5. 提供可运行的启动命令和 API 示例。
6. 编写 API 合约测试、检索冒烟测试和错误场景测试。
7. 记录运行环境、模型版本、索引版本和评测命令。

**验收标准：**

- 服务能够正常启动。
- API 可以返回真实检索结果。
- 返回的证据能追溯到结构化数据。
- 核心测试通过，异常请求有明确响应。
- 新环境按照 README 可以复现基本运行流程。

### P9：Agent 扩展（可选）

**目标：让系统根据检索情况选择下一步操作。**

只有 P5 的基线评测和 P8 的基本接口稳定后，才考虑实现。

第一版采用简单单 Agent，不引入多 Agent 编排框架。

允许的工具包括：

- `search_subjects`：检索作品。
- `search_characters`：检索角色。
- `search_episodes`：检索章节。
- `get_related_subjects`：查询实体关系。
- `ask_user_for_clarification`：在信息不足时请求补充线索。

Agent 的任务是判断是否需要补充查询、换检索入口或追问用户，不负责取代底层召回算法。

**验收标准：**

- Agent 调用的工具均有明确输入和输出。
- 工具结果可追溯到实际数据库。
- 对比启用与禁用 Agent 时的检索质量、额外延迟和调用成本。
- 只有在实测证明有价值时才保留该模块。

## 五、工程质量与通用约束

以下要求适用于全部阶段。

### 5.1 代码质量

- 采用清晰的模块职责，不把所有逻辑堆在一个脚本中。
- 为关键数据转换、文档构建和检索逻辑编写测试。
- 对异常记录进行日志记录，避免静默跳过。
- 使用配置文件或统一配置模块管理路径、模型名称和批次大小。
- 不在代码中硬编码本机专属路径。
- 正式脚本应具有明确的命令行参数与退出状态。

### 5.2 数据安全与可恢复性

- 不修改或覆盖 `data/raw/`。
- 在删除、覆盖数据库或重建索引之前进行明确检查。
- 生成中间数据时采用临时文件加原子替换等安全方式。
- 记录索引构建进度，支持中断恢复。
- 不将完整原始数据集、模型权重或大型索引默认提交到 Git。
- 在公开项目中说明数据来源、使用范围和相关授权情况；未经确认，不要把完整数据集重新打包公开分发。

### 5.3 可复现性

每次构建和评测都应记录：

- 数据源版本或文件校验信息
- 数据处理配置
- Embedding 模型名称及版本
- 文档构建规则版本
- 索引版本
- 测试集版本
- 评测指标与运行环境

这样才能区分检索效果的变化究竟来自模型、数据、文档规则还是融合算法。

## 九、最终项目评价标准

PlotSeeker 不以代码行数、向量条数或 Agent 的复杂程度作为成功标准。

真正重要的是：

- **数据工程：**能否把大规模原始数据可靠地转化为结构化知识库。
- **检索工程：**能否结合关键词、语义和实体关系解决模糊查询。
- **评测能力：**能否用标准答案证明各模块的作用，而非只展示成功案例。
- **工程可靠性：**能否重复构建、恢复中断、追踪证据并控制资源。
- **成果可展示性：**能否通过 Demo、架构图、测试集和评测报告清楚证明项目价值。

最终目标是交付一个可运行、可复现、可评测的 RAG 系统，并在真实测试基础上总结检索质量与工程优化成果。
