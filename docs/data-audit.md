## 9. 首期索引范围建议

以下范围基于本次实测数量给出。P3/P4 仍应按规划先做小规模闭环，再用评测决定是否扩大。

### 9.1 作品文档

- 实测作品 695,909 条，简介非空 572,333 条。
- 建议首期纳入“简介非空”的作品；若需要进一步控量，先取非 NSFW 且简介非空的 529,003 条做 1 万条以内的索引实验，再逐步扩容。
- 文档必须合并 `name`、`name_cn`、infobox 中文名和 `别名`，并把 `nsfw`、`type`、`platform`、年份放入元数据，不要用其替代文本。

### 9.2 角色文档

- 实测角色 223,927 条，简介非空 170,975 条，可映射到作品且简介非空 170,491 条。
- 建议首期纳入“简介非空且能通过 `subject_characters` 映射到作品”的角色；没有简介但名称/别名可靠的角色可后续补充。

### 9.3 章节文档

- 实测章节 1,709,524 条，描述非空 110,840 条，所属作品存在 1,694,367 条；描述非空且所属作品存在 110,157 条。
- 抽样中疑似剧情 4.6%、制作信息+剧情混合 2.3%。建议 P3 仅纳入通过质量规则且能映射到作品的章节，并保存过滤原因。

### 9.4 别名与实体关系

- 作品 infobox 中可解析出别名的文档：108,652 条。
- 角色和章节命中后必须通过 `subject_characters` 映射回作品，章节还要校验 `episode.subject_id`，避免把孤儿记录当作证据。

## 10. 对 P2 结构化库的 Schema 建议

本建议来自实际字段，不删除原始业务字段：

```text
subject(id PK, type, name, name_cn, infobox_raw, platform, summary, nsfw, tags_json,
        meta_tags_json, score, score_details_json, rank, date, favorite_json, series,
        source_file)
episode(id PK, name, name_cn, description, airdate, disc, duration, subject_id FK,
        sort, type, source_file)
character(id PK, role, name, infobox_raw, summary, comments, collects, source_file)
person(id PK, name, type, career_json, infobox_raw, summary, comments, collects, source_file)

subject_characters(subject_id, character_id, type, ord, PRIMARY KEY(subject_id, character_id))
subject_persons(subject_id, person_id, position, appear_eps,
                PRIMARY KEY(subject_id, person_id, position))
subject_relations(subject_id, relation_type, related_subject_id, ord,
                   PRIMARY KEY(subject_id, related_subject_id, relation_type))
person_characters(person_id, subject_id, character_id, type, summary,
                    PRIMARY KEY(person_id, subject_id, character_id))
person_relations(person_type, person_id, related_person_id, relation_type,
                 spoiler, ended,
                 PRIMARY KEY(person_type, person_id, related_person_id, relation_type))
```

- 索引：`episode(subject_id)`、`subject_characters(character_id)`、
  `subject_persons(person_id)`、`subject_relations(related_subject_id)`、
  `person_characters(character_id)`、`person_relations(person_type, person_id)`。
- 原始 `infobox` 以文本形式保留，解析结果另行生成，不覆盖原文。
- 代码含义未确认的字段（`type`/`platform`/`position`/`relation_type`/`person_type`/`role`）
  先按整数或原值存储，另建码值说明表，不写入推测性标签。
- `person_relations` 不应直接对 person/character 建强外键：两种 ID 空间存在大量重叠，P2 应以 `person_type` 作为命名空间保存原值，并在文档层说明其含义仍需确认。
- 建议为每个表保留 `source_file`，配合实体 ID 即可追溯回原始 JSONL。

## 11. 数据异常与待确认问题

- 本次全量读取未发现 JSON 解析、解码或非对象记录错误。
- `episode.description` 混有制作名单与剧情文本；P3 必须按质量规则过滤并保留过滤原因。
- `person_relations.person_type` 取值为 `crt` / `prsn`；抽样中 `crt` 记录的名称通常对应角色，但 person 与 character 的 ID 集合有 102,175 个重叠，仅凭 ID 不能唯一判定。P2 应按 `person_type` 分命名空间保存，不做跨表强外键。
- 关联表自然键重复可能来自原始数据重复导出，重复数量已在第 4 节列出；P2 导入必须使用唯一约束或显式去重策略。
- 繁体/简体分类基于启发式字符对，仅用于覆盖率；如需要精确统计，P3 可引入 OpenCC 做对照实验。
