# P7 扩容分析（未执行全量）

> 更新时间：2026-10-21
> 结论：**不启动百万级全量编码**，只记录 10,000 篇实测预算和扩容前检查项。

## 1. 为什么不直接外推

10,000 篇样本的编码速度、内存和索引体积只能作为初步基准：

- HNSW 构建时间和磁盘占用不是严格线性。
- 文档长度分布、batch 命中率、GPU 热状态会影响吞吐。
- 全量 846,606 篇中包含大量重复或近似文本，去重后规模未知。
- 关键词索引和向量索引同时扩容时，查询延迟和磁盘压力需要重新测量。
- 当前评测集不是独立人工查询集，扩容收益无法直接用现有指标证明。

因此下文的“线性估算”只用于预算量级，不作为验收结果。

## 3. 全量规模预算（未验证）

- P3 文档总数：846,606 篇，约 942 MiB 文本。
- 相对 10k 的倍数：约 84.66 倍。
- 线性估算向量索引：约 9.6 GiB。
- 线性估算关键词索引：约 5.1 GiB。
- 线性估算编码时间：约 4.4 小时（53.41 docs/s，未计中断与重试）。

- 现有 SQLite：1.645 GiB；BGE-M3 权重：2.27 GB。

这些数字只说明“磁盘量级可能足够”，不能说明全量构建能在可接受时间内完成。

## 4. 全量启动前必须完成

- [ ] 文本级去重：精确重复、近似重复、同一实体多文档的统计。
- [ ] 实际 token 总量与 1024 token 截断比例。
- [ ] 全量关键词索引构建时间、体积、查询 P50/P95。
- [ ] 全量向量编码的分批预算、GPU 温度/显存峰值、失败重试。
- [ ] checkpoint 断点恢复在真实全量规模下至少演练一次。
- [ ] 失败回滚：保留旧索引、临时目录、原子替换和磁盘水位告警。
- [ ] 索引版本与模型 revision 绑定，禁止混用旧向量。
- [ ] 用独立人工查询集复测；现有开发集不足以证明扩容收益。
- [ ] 明确是否值得索引全部角色/章节，而不是只扩大作品文档。
- [ ] 人工确认资源预算和可接受的最长构建时间。

## 5. 建议的扩容顺序

1. 先做文本去重和 token 统计，得到真实文档规模。
2. 在 50k / 100k 规模做一次可控扩容实验，记录吞吐、体积、延迟。
3. 用独立查询集比较 10k 与扩容后的 Recall/MRR；若没有提升，停止扩容。
4. 通过后再评估全量，不在当前阶段直接编码 84.6 万篇。

## 6. 当前决定

P7 暂停，等待人工确认资源预算和评测集质量。P4/P5/P6/P8 的 10k 闭环保持可用。
